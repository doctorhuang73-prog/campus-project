# 安卓到 iOS 的迁移边界

## 为什么初版使用 SwiftUI

原项目是 Android Kotlin/Java + Compose + 旧 View 混合工程；网络解析、插件沙箱、凭据与后台任务有大量 Android/JVM 依赖。直接增加 iOS 编译目标无法工作。本初版沿用产品页面组织与已公开的教务协议映射，用原生 SwiftUI/WKWebView/Foundation 建立可独立构建的 iOS 工程。没有宣称原安卓程序已经整体跨平台化。

## 数据与失败处理

- `School.baseURL()` 只接收无凭据/票据/片段的 HTTPS 根地址。不能将具体登录 HTML 地址当成教务前缀。
- WKWebView 使用 nonPersistent 数据容器，允许 HTTPS 的 SSO 重定向；当前主页面域名始终显示。
- API 请求只导入属于配置教务域名的 Cookie；网络重定向不离开当前教务 origin。系统 TLS 验证保持开启。
- 同步包含课表与全部成绩页，全部成功才更新缓存。失败保持旧缓存和旧同步时间。
- 修改学校/学期、切换演示或退出时改变 generation，并取消旧客户端，异步旧结果不能覆盖当前状态。
- 非标准课表解析失败时明确报错，未知周次不默认成每周上课。
- 未做用户学校实测，不使用作者的演示截图证明真实登录或选课成功。

## 分支约定

初版经云端验证后在 main 标记 `v0.1.0`。后续可按任务建立 `feature/school-adapters`、`feature/course-selection`、`feature/widgets` 等分支；通过 CI 后再合并。避免把每项功能同时改在 main 上。

## 验证层次

1. 单元测试验证周次、学期、URL、编码、分页解析及 GPA。
2. GitHub macOS 实际编译模拟器与 iPhone 二进制。
3. 模拟器启动并截取四页面，检查显示。
4. Windows 本地签名安装后的 iPhone 真机与学校账号验证，需要用户后续完成；不能由前三层代替。
